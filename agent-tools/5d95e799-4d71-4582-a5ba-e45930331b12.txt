# Forever API ledger

The single place where auctionhouse.fyi records what is known about the WoW: Forever APIs and client behaviours the addon (`addon/AuctionHouseFYI/`) and the desktop app rely on, and how it is known (AGENTS.md rule 2). Code cites this file. Update it whenever a `/dump`, probe or source read settles something.

Rows marked (wowzers) are copied from wowzers' ledger (`docs/forever-api-ledger.md` at `31a5fc3`) with their evidence status unchanged: wowzers' in-game observations are Jared's, on his client, with wowzers' addon. Everything new to this project is UNVERIFIED until Jared runs the checks at the end.

Evidence tags:

- `in-game`: run on our own client (Jared's). Record the build and date.
- `measured`: someone else ran it on a live Forever client and published the result.
- `source`: Blizzard's Forever-branch UI source or its generated API docs.
- `community`: a single report, not independently confirmed.
- `UNVERIFIED`: inferred. Must not be relied on until upgraded.
- `local`: observed on a dev machine's disk, registry or process list (outside the client).

Not evidence: memory, LuaLS/Ketho autocomplete, Retail wiki pages, a Retail checkmark, `WOW_PROJECT_ID == 1`.

Client under test (wowzers): beta 1.60.1, builds 69893 → 69913 → 69977 → 70009. Interface 16001. Beta folder `World of Warcraft\_classic_beta_\`, exe `WowB.exe`.

### Buy orders versus auction bids (research, 2026-10-01)

Source checked: Forever generated auction API and Forever item-buy UI. These are source evidence, not a new in-game observation.

- `GetReplicateItemInfo(i)` declares numeric returns 8 = `minBid`, 9 = `minIncrement`, 10 = `buyoutPrice`, 11 = `bidAmount`. Existence is source-confirmed; populated values and their exact behavior on our Forever client remain UNVERIFIED. The scanner now optionally reads these three numeric bid fields through `plain`, with missing/secret/invalid values left unknown. Strip-v1 kind 5 wraps the unchanged kind-3 book with bid-detail rows; kind 3 still has no bid-price fields. Its zero-price entries count auctions without buyouts, not buyer orders.
- `GetItemSearchResultInfo` declares `minBid`, `bidAmount` and `buyoutAmount` on a particular auction. The item-buy UI selects an existing `auctionID` before bidding/buying. `PostItem` declares seller bid/buyout prices; `PostCommodity` declares a unit price. No standing buy-order posting or public buy-order-book API was found in the generated API. The inference is that the available market is seller listings with bids attached to individual auctions, rather than an exchange with independent bids and asks. This does not prove that every beta server behavior matches the source.
- The website shows buyout depth plus optional current bids and minimum bidding prices on listed auctions. Starting bids are seller terms, not observed buyer demand; current bids are not independently fillable buy orders or a complete bidding history. Do not label these as a two-sided exchange book. Missing bid detail does not stop buyout capture. Never collect bidder or seller identity.

## Secret values (wowzers)

`issecretvalue(v)` is the only valid test; `type(secret)` returns the real type; `==`, `<`, arithmetic, `#`, table keys and truth tests on a secret throw; `tostring` and `..` produce a secret string. The auction house read calls have no `SecretReturns` (source), but every value the addon reads goes through `ns.plain` (a secret reads nil and is skipped), and nothing secret reaches the strip.

## Behavior gotchas (wowzers)

- Registering an event the client doesn't know throws and aborts the rest of the file: every registration goes through `pcall`.
- `OnUpdate` `elapsed` is quantized to 1 ms.
- `string.format("%d", n)` throws for `n` past 2³¹ − 1: format item keys with `%.0f`.
- A `.toc` edit or a new addon folder needs a full client restart, not `/reload`.

## Books-only acquisition policy (2026-09-29)

The current addon requests only replicate books; missing APIs/events, a recent attempt or a ten-second no-answer timeout never starts a browse fallback. The desktop decodes legacy kind-2 frames for diagnostics but never queues them for upload. Catalogue collection now observes the player's browse events passively; it does not start or page a browse. No new game API is introduced by this change, and no additional in-game behavior is claimed as verified.

Offline validation covers decision guards, replicate timeout with no fallback, player-search deferral, a real Lua book export through the Rust decoder, and ignoring legacy summaries in the desktop upload flow. In game, `/reload`, open an auctioneer with the paired desktop app running, inspect `/ahf status` and BugSack, then `/ahf scan`. A successful read should produce a book; missing/throttled/no-answer replication should show waiting without a browse or summary upload. Verify a second manual attempt within twenty minutes does not call replication again. These steps remain pending on Forever.

## Opening latency (2026-10-05)

The addon now checks on the first timer frame after `AUCTION_HOUSE_SHOW`, without the inherited two-second delay. A temporarily busy message system gets opening checks every 0.1 s for at most 60 s, including with `live` disabled, instead of waiting for the next 30 s live check. The current opening, search hooks, settings, freshness, combat and replicate interval still guard each request. The first read batch starts inside `REPLICATE_ITEM_LIST_UPDATE`; remaining reads and packing still yield in bounded batches so a large market does not run in one frame. For a desktop whose helper announces kinds 6/7, packing queues fragments as it proceeds and updates the checksum incrementally; it does not construct one packed string before sending. Legacy desktops retain the full kind-5 transfer. Pixels still wait for the server response and the merged read.

No new WoW API is introduced. Fake-client Lua tests cover prompt requests, initial readiness, the game's favourites, player searches, close/reopen cancellation, bounded waiting and a multi-batch book passing through the Rust pixel decoder. These do not measure live server latency or client frame cost; the new scheduling remains UNVERIFIED on Forever.
